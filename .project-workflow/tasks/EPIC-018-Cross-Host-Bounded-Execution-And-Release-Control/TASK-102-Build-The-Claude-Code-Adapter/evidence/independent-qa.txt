### Critical — Hook activation and failure handling are not fail-closed

The prompt is supplied when the Claude process starts, before SessionStart activation has been observed. It runs under `bypassPermissions`. Consequently, Claude may execute tools before the supervisor knows whether the policy hook works.

The plugin’s command hooks have five-second timeouts. Current Claude documentation says command-hook startup failures and timeouts are non-blocking, including for PreToolUse. SessionStart cannot block at all, and PostToolUse occurs after the tool has executed. The implementation detects missing SessionStart only during closeout, after mutations may already have occurred. [Claude’s hooks reference](https://code.claude.com/docs/en/hooks) documents these native boundaries.

The plugin also omits PostToolUseFailure and PostToolBatch, so a failing Bash command that partially mutates state is not checked immediately, and the agentic loop is not synchronously stopped before another model call.

Evidence: [claude_adapter.py](</private/tmp/pw-cross-host.TywgOX/src/project_workflow/claude_adapter.py:809>), [hooks.json](</private/tmp/pw-cross-host.TywgOX/src/project_workflow/claude_plugin/project-workflow-execution-control/hooks/hooks.json:1>), [hook exception handling](</private/tmp/pw-cross-host.TywgOX/src/project_workflow/claude_adapter.py:654>), [missing-hook test](</private/tmp/pw-cross-host.TywgOX/tests/test_claude_adapter.py:324>).

Required correction:

- Do not submit the material prompt until stream initialization and the package-owned SessionStart handshake are positively observed.
- Use native permission/sandbox controls that still deny unapproved tools, commands, and paths if a command hook is missing, crashes, or times out; do not make `bypassPermissions` the sole fallback.
- Make hook launcher failures exit with native blocking semantics.
- Cover PostToolUseFailure and a synchronous terminal boundary such as PostToolBatch where applicable.
- Add native countercases for missing handler, wrong interpreter, crash, timeout, lock contention, parallel hooks, managed-policy exclusion, and partial command mutation.

Affected proof: child AC2, AC3, AC5; parent AC3, AC4, AC10, AC12.

### High — The managed CLI and packaged hook do not reliably load the adapter

All three managed CLI copies are byte-identical, but they import `project_workflow.claude_adapter` dynamically. The managed launcher executes its standalone `workflow.py` with `python3`; a normal consumer installation does not thereby install `project_workflow` into that interpreter.

The packaged hook has the same defect: it runs `python3 -m project_workflow.claude_adapter`. Direct inspection on this host proved `/opt/homebrew/bin/python3` raises `ModuleNotFoundError`, while only the repository `.venv` imports the package. Existing tests import the source package inside that virtual environment and never exercise the managed launcher-to-hook interpreter chain.

Evidence: [managed workflow launcher](</private/tmp/pw-cross-host.TywgOX/.project-workflow/cli/workflow:1>), [managed CLI import](</private/tmp/pw-cross-host.TywgOX/.project-workflow/cli/workflow.py:16740>), [packaged hook](</private/tmp/pw-cross-host.TywgOX/src/project_workflow/claude_plugin/project-workflow-execution-control/scripts/project-workflow-claude-hook:1>), [mocked core-receipt test](</private/tmp/pw-cross-host.TywgOX/tests/test_execution_control_contract.py:608>).

Required correction: make the managed CLI and hook use an exact package-capable interpreter, or ship a self-contained managed adapter beside `workflow.py`. Prove fresh init, canonical upgrade, no-op, disable/uninstall, and retained-wheel execution without relying on the repository virtual environment.

Affected proof: child AC4, AC5, AC7; parent AC10, AC13.

### High — Timeout does not terminate the execution tree

`_StreamProcess` terminates or kills only the direct Claude process. It does not create or terminate a process group. Hook handlers, Bash tools, tests, background commands, or subprocesses can therefore survive the elapsed-time boundary and continue operating.

The daemon reader threads are neither joined nor synchronously drained. Once the direct process exits, the receive loop can observe `poll() != None` before its reader has queued the final result. Stderr and protocol-event collections are also unbounded.

Evidence: [_StreamProcess creation](</private/tmp/pw-cross-host.TywgOX/src/project_workflow/claude_adapter.py:669>), [stop implementation](</private/tmp/pw-cross-host.TywgOX/src/project_workflow/claude_adapter.py:723>), [stream loop](</private/tmp/pw-cross-host.TywgOX/src/project_workflow/claude_adapter.py:847>).

Required correction: create an isolated process group/session, terminate and reap the full tree, join/drain readers before classifying exit, bound retained output, and add real subprocess tests covering buffered terminal output, child survival, SIGTERM escalation, timeout, and cleanup.

Affected proof: child AC3; parent AC4 and AC10.

### Medium — Capability probing is not a truthful current-contract test

The probe requires every flag to appear in `claude --help`, but the current CLI documentation explicitly says help does not list every flag. This can misclassify a supported installation as incompatible. Conversely, substring presence does not prove behavioral support.

The current native budget contract says full background-subagent cap enforcement requires Claude Code 2.1.217 or later, yet the adapter accepts any exact version string whose help contains the expected tokens. [Claude CLI reference](https://code.claude.com/docs/en/cli-reference).

Required correction: maintain a supported-version/capability matrix and verify binding behavior through non-model probes or the mandatory canary. Probe authentication under the same isolated configuration used for dispatch, and classify managed-policy restrictions separately from generic incompatibility.

Affected proof: child AC1 and AC5; parent AC12.

### Medium — Documentation overstates native hook behavior

README describes SessionStart, PreToolUse, PostToolUse, and Stop as “blocking.” Native Claude semantics only permit PreToolUse to deny a pending tool; PostToolUse happens after execution, SessionStart has no decision control, and blocking Stop means forcing Claude to continue rather than terminating it.

Evidence: [README.md](</private/tmp/pw-cross-host.TywgOX/README.md:731>), [official-contract record](</private/tmp/pw-cross-host.TywgOX/.project-workflow/tasks/EPIC-018-Cross-Host-Bounded-Execution-And-Release-Control/TASK-102-Build-The-Claude-Code-Adapter/evidence/official-claude-contract.md:14>), [Claude hooks reference](https://code.claude.com/docs/en/hooks).

Required correction: describe each hook’s actual native authority and distinguish prevention, post-execution detection, supervisor interruption, and closeout rejection.

Affected proof: child AC7; parent AC10, AC12, AC16.
