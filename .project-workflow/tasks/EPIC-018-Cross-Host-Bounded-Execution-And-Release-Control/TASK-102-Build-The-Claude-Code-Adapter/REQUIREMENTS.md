## Intent

Make Claude Code a truthful subordinate execution host for the approved Project Workflow envelope,
using current native print-mode, streaming, hook, permission, turn, budget and timeout controls while
leaving lifecycle, candidate, QA, release and shared-state authority in Project Workflow core.

## Intent Spine

- OC1 — Completion capability: A Coordinator can dispatch one sealed material unit through one exact supported Claude Code installation and receive one typed core-owned terminal receipt.
- OC2 — Material capabilities: Exact capability inspection/probe, blocking PreToolUse enforcement, aggregate native counts, streamed result supervision, finite budget/turn/elapsed control, package assets and truthful status/Doctor projection.
- OC3 — Success journey: One clean disposable repository runs the public `project execute` path, activates the package-owned hooks, makes only the required scoped change, preserves source identity and records the exact Claude-native cost/turn/tool/path result.
- OC4 — Successful-but-wrong result: Static plugin files, CLI help, mocked output or a completed Claude turn appear green while hooks did not run, scope drifted, the required output is absent, or Project Workflow did not persist the receipt.
- OC5 — Exclusions: No host-neutral metric conversion, candidate promotion, QA ownership, release executor, external installation/adoption claim, other-host support claim or Strategic Advisor ownership.
- OC6 — Assumptions: The final real canary requires an exact locally available, authenticated Claude Code runtime whose managed policy permits the package hook; absence remains a precise unsupported/setup state.
- OC7 — Authority source: Parent Epic Intent and approved decomposition row.

## Child Charter

### Inherited Invariants

- Project Workflow remains the only product owner, repository owner, Coordinator, lifecycle, verification campaign, QA verdict, candidate authority, and shared-state writer.
- Read-only and cheap deterministic work does not launch another model or require campaign ceremony.
- Material work in a supported trusted installation cannot mutate, validate broadly, remediate QA, promote a candidate, or release outside the controlled path.
- The worker cannot amend its sealed execution identity, write scope, permitted operations, proof obligations, or finite limits.
- Limits pause or block and keep missing proof visible; they never manufacture a pass.
- One independent QA pass creates one durable findings set. In-scope remediation is automatic and bounded; only affected proof and unresolved findings are rechecked; a second broad QA is prohibited.
- Continuation requires named material progress. An identical or no-progress repeat is denied.
- Working revisions, verification candidates, and release candidates have distinct semantics.
- Release candidate promotion occurs only after all required implementation, verification, QA, and affected-proof obligations pass.
- Release runs predeclared operations against one clean frozen candidate and has no source repair, QA, or replacement-candidate authority.
- Host adapters enforce the same decisions and receipt meanings but may use different native units and mechanisms.
- Unsupported or unknown binding host capability fails closed for material work and cannot be advertised as supported.
- Codex and Claude Code are the minimum initial supported hosts. No other host inherits the claim.
- All shipped core and adapter assets come from the Project Workflow repository and package.
- Automated, host-runtime, package, merge, publication, installation, adoption, effectiveness, and owner-acceptance proof remain separate.

## Goal

Provide the Claude Code half of the minimum supported-host contract so material work is enforced by
the same Project Workflow decisions and receipt meanings without pretending Claude-native dollars,
turns, tools or elapsed time are Codex units.

## Non-Goals

- Cross-host conformance completion, recurrence dogfood and delivery closeout owned by TASK-103.
- Candidate promotion, QA remediation and fixed release behavior owned by TASK-100.
- Installing Claude Code into a user environment, authenticating an account, publishing a package,
  enabling a plugin in a consumer project or claiming adoption without separate evidence.
- Interactive/web/desktop Claude surfaces, other hosts, normalized cross-host budgets, or a new
  workflow writer.

## Users & Context

Project Workflow Coordinators and maintainers running approved material work on Claude Code from a
trusted local installation. Read-only diagnosis and cheap deterministic operations continue directly
without launching Claude.

## Requirements (Outcome-Focused)

- R1 — Validate an exact absolute `claude` executable, SHA-256 identity, expected version, trust,
  model, prompt, permitted tools/commands, required outputs and typed Claude-native finite limits.
- R2 — Keep read-only inspection model-free and executable-free; material dispatch probes exact CLI
  flags and then verifies live stream initialization, loaded plugin/hook state and terminal result.
- R3 — Launch only non-interactive print mode with `stream-json`, verbose hook events, explicit
  `--max-turns`, `--max-budget-usd`, allowed/disallowed tools, no session persistence and finite
  process timeout.
- R4 — Ship package-owned Claude Code plugin assets with blocking SessionStart, PreToolUse and
  PostToolUse/Stop coverage that bind the sealed workspace root, tool/command/write scope, aggregate
  retries/tests/workers/changed paths and sticky terminal denial.
- R5 — Translate Claude result subtype, cost, turns, usage, hook events, tool observations and exact
  final Git state into the same host-neutral terminal receipt shape while preserving native units.
- R6 — `project execute` must route sealed Claude settings through this adapter and Project Workflow
  core alone writes Coordinator state; no adapter command promotes candidates, performs QA or releases.
- R7 — Status and Doctor distinguish inspectable, disabled, unavailable, untrusted, version-stale,
  policy-blocked, hook-disabled and verified-at-dispatch states without overclaiming package presence.
- R8 — Retain package archives and a real supported Claude Code canary when the required runtime and
  authentication are available; if not, finish source/package proof but keep AC10 and support status
  blocked with the exact missing capability.

## Acceptance Criteria (Verifiable)

- AC1: Exact Claude executable/version/configuration and binding capabilities are inspectable,

- AC2: Blocking package-owned hooks enforce the sealed workspace, tools, commands, writes, aggregate
  activity and sticky terminal state for main-agent and subordinate activity surfaced by Claude hooks.
- AC3: Print-mode supervision uses explicit native budget/turn/elapsed/tool controls, parses streamed

- AC4: `project execute` dispatches only current sealed Claude settings and Project Workflow core

- AC5: Packaged assets plus status/Doctor truthfully report active-at-dispatch, inspectable, disabled,
  incompatible, untrusted, unavailable and managed-policy-blocked states.
- AC6: One real supported Claude Code canary proves hook activation, exact scoped required output,

## Decisions (Resolved)

- Use Claude Code CLI print mode rather than the Agent SDK to keep the packaged adapter dependency-free
  and aligned with the approved current CLI mechanism.
- Treat `--max-budget-usd`, `--max-turns`, tool calls and elapsed time as distinct Claude-native units.
- Load the package-owned plugin with `--plugin-dir` for the sealed dispatch; do not claim user/project
  installation from package presence.
- PreToolUse denials remain binding even when Claude permission mode would otherwise allow the tool.
- A real canary is required for AC6 and parent AC10; unavailable local runtime or authentication is a
  precise delivery blocker, not permission to substitute tests.
