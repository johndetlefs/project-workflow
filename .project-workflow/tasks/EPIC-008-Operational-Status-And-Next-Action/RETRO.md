# Epic Retro

- Title: Operational Status And Next Action
- Last updated: 2026-07-22

## Lessons

- A useful status command must separate workflow health, proof progression, and delivery progression rather than compress them into one confidence label.
- Existing repository artifacts were sufficient sources of truth; the product needed a typed read projection and deterministic precedence, not a new status store.
- Reusing Doctor evaluation prevented accepted-warning and strict-mode drift. Reusing lifecycle gates prevented status from recommending invented transitions.
- Local Git ancestry and explicit receipts support bounded delivery claims, but repository completion remains distinct from merge, release, publication, deployment, and adoption.
- Disposable generated-helper journeys plus file/Git identity checks materially strengthened confidence beyond unit fixtures alone.
